# Agg-API-DSM 架构设计

一个套件、一个二进制、一个端口，同时提供两个上游的能力。
下游只认一个地址、一个 API Key，由**模型名**决定走哪条链路。

---

## 一、为什么不是「把两堆代码拼起来」

两个上游的差异不在语言（都是 Go），而在**关注点纠缠方式**：

| | agnes-hub-go | M365-Copilot2API |
|---|---|---|
| 核心难点 | 多账号池化、RPM 严格节拍限流、二维自适应校准 | WebSocket 长连接、OAuth 授权、图片生成配额 |
| 结构 | pool / pacer / hub / relay / intent | auth / chathub / mcp / outbound / web |
| 依赖 | 零第三方 | 7 个第三方 |

直接拼在一起会得到两个互不相干的 `main`，共享不了任何东西 —— 那不叫合并，叫**打包**。

真正的合并点是：**「账号池 + 限流」不是 Agnes 的私产，是通用能力。**
Copilot 同样有配额、同样会 429、同样需要冷却与轮换。
把它从 Agnes 的业务里**上提**到网关层共用，两个上游都受益 ——
这就是「互补而非重叠」的落点。

## 二、分层

```
┌─────────────────────────────────────────────────────┐
│  web        统一控制台（一个界面管两个上游）           │
├─────────────────────────────────────────────────────┤
│  gateway    路由 / OpenAI 兼容端点 / 下游 Key 校验     │
│             ★ 不认识任何具体上游                       │
├─────────────────────────────────────────────────────┤
│  pool       账号池（两个上游共用）                     │
│  pacer      RPM 限流（两个上游共用）                   │
├─────────────────────────────────────────────────────┤
│  provider   接口层：Provider / Model / ChatRequest     │
│  ├── agnes     Agnes 协议适配                          │
│  └── copilot   Copilot 协议适配（WebSocket）           │
└─────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：`provider` 不反向依赖 `gateway`。
新增第三个上游时，只需实现 `provider.Provider` 并在装配处注册一行，
网关核心与两个既有上游都零改动。

---

## 三、路由：模型名即链路

模型名全局唯一，注册时建立索引，请求时一次查表。
**重复的模型名在注册阶段就报错**，而不是等到运行时把请求发错上游。

命名约定用前缀区分链路，让用户在客户端里一眼看出走的是哪条：

| 前缀 | 上游 | 例 |
|---|---|---|
| `agnes-` | Agnes AI | `agnes-auto` |
| `copilot-` | M365 Copilot | `copilot-auto` / `copilot-chat` / `copilot-image` |

`/v1/models` 的 `owned_by` 填上游名，客户端据此也能判断。

---

## 四、能力声明，而不是靠猜

每个模型声明自己的能力位（`CapText` / `CapImage` / `CapVision` / `CapVideo` / `CapDoc` / `CapStream`）。

网关**在转发前先查一次**，不支持就直接返回明确错误：

> 比把请求发出去、拿回一个语焉不详的上游报错要好 ——
> 用户需要知道「是我不该这么用」，而不是「上游出了点问题」。

---

## 五、依赖取舍

上游两边一个是零依赖、一个是 7 个。新项目取中间路线，**只留标准库无法替代的**：

| 依赖 | 保留？ | 理由 |
|---|---|---|
| `gorilla/websocket` | ✅ | Copilot 走 WebSocket 长连接，标准库没有客户端实现。**唯一不得不留的** |
| `golang.org/x/crypto` | ✅ | 仅用于 bcrypt 口令散列。**固定在 v0.31.0** —— v0.57+ 要求 go ≥ 1.26 |
| `google/uuid` | ❌ | `crypto/rand` 拼 16 字节即可（原 15 处引用全可替换） |
| `ledongthuc/pdf` | ❌ | 仅 1 处，PDF 附件解析。首版不做附件 |
| `xuri/excelize` | ❌ | 仅 1 处，Excel 附件解析。同上 |
| `tiktoken-go` | ❌ | 仅 1 处，token 估算。改用字符数近似 |
| `golang.org/x/net/proxy` | ❌ | 仅 1 处，SOCKS 代理。首版只支持 HTTP 代理 |

**Go 版本取 1.22**（不是 M365 的 1.25）：
- 1.22 是「`ServeMux` 支持 `/v1/videos/{id}` 路径参数」的最低版本，够用
- 避免依赖 `go1.25.0` 工具链的自动下载（受限网络下会失败）
- 代价：`x/crypto` 必须固定旧版本

## 六、明确不迁移的部分

| 项 | 决定 | 理由 |
|---|---|---|
| **OAuth 设备码授权** | ❌ 不迁移 | 用户明确说用不上 |
| fnOS 相关工具链 | ❌ 不迁移 | 只做群晖 |
| M365 的 Python 脚本 | ❌ 不迁移 | 是开发/运维辅助，非运行时 |
| 附件解析（PDF/Excel） | ⏸ 首版不做 | 可去掉两个重依赖，后续按需加回 |

## 七、打包与分发

沿用 M365 的既有做法（已验证可用）：

- **打包**：`spk/build-spk.sh`（bash）。已在 Git Bash + GNU tar 1.35 下验证
  **保留权限位** —— M365 README 里「Windows 的 tar 不保留权限位」指的是系统自带的
  bsdtar，不是 Git Bash 的 GNU tar
- **套件源**：沿用 M365 的 `gh-pages` 分支
- **桌面图标**：沿用 M365 的 `ui/` 全套（`com.kosje.aggapi` 命名 + 7 种尺寸）
- **端口**：**4444**。刻意避开两个上游各自占用的 4141（M365）与 4142（Agnes）——
  合并后只装这一个套件，但若用户机器上还留着旧的单上游套件，端口不重叠才能并存排查
